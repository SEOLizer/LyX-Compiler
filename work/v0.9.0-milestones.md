### WP-1.1-A: Soft-Keyword-Infrastruktur ✅

**Ziel:** `defer`, `range`, `wraps` und künftige Kontextkeywords sicher vom
Bezeichner-Namensraum trennen, ohne Breaking Changes an bestehenden Variablen-
oder Funktionsnamen.

**Aktueller Stand:** `defer` ist als Soft-Keyword implementiert (Ident-Vergleich
im Stmt-Parser, `src/parser.lyx:1367`). `range` und `wraps` fehlen noch.

**Zu implementieren:**

1. Zentrale Hilfsfunktion `_isSoftKw(src, tok, keyword)` → int64 im Parser, die
   ident-Token gegen einen Literalstring prüft — vermeidet überall verstreute
   `_tokTextEq`-Aufrufe.

2. `range` als Soft-Keyword für `for x in range(n)` und Slice-Ausdrücke:
   ```lyx
   for i in range(0, 10) { ... }
   for i in range(10)    { ... }  // 0..n-1
   ```
   Parser-Rule: In `parseForStmt`, nach `for <ident> in`, wenn folgendes Token
   `range` ist → `NK_FOR_RANGE` mit Start/Stop/Step-Children.

3. `wraps` als Soft-Keyword für arithmetische Überlauf-Semantik (Annotation an
   Ausdrücken/Typen):
   ```lyx
   var x: int32 wraps := 0;        // overflow wraps around
   var y: int32 wraps = 255 + 1;   // = 0
   ```
   Parser emittiert `NK_VAR_DECL` mit gesetztem `VAR_FLAG_WRAPS`-Bit in `iVal`.

4. Lookahead-Prädikat `_looksLikeSoftKw(parser, keyword)` — prüft aktuelles
   Token und einen Schritt Lookahead, um Konflikte mit gleichnamigen Funktionen
   (`defer()`, `range()`) zu vermeiden.

**Akzeptanzkriterien:**
- `var defer: int64 := 5;` kompiliert ohne Fehler (defer als Bezeichner)
- `defer PdfFree(doc);` wird als Defer-Statement erkannt
- `for i in range(10)` erzeugt korrekten IR-Loop
- `var x: int32 wraps := 0xFF + 1;` emittiert ADD ohne Overflow-Check

### WP-1.1-B: Float-Literal vs. Methoden-Dot ✅

**Ziel:** Lexer unterscheidet sicher zwischen Float-Literalen (`42.0`) und
Methoden-Aufrufen auf Integer-Primärausdrücken (`42.toStr()`).

**Problem:** Aktuell wird `42.toStr()` als Float-Token `42.` + `toStr()`
geparst, was falsche Token-Grenzen erzeugt.

**Zu implementieren:**

1. Im Lexer: nach Digit-Sequenz, wenn Punkt gefolgt von Alpha (`[a-zA-Z_]`)
   statt Digit → kein Float, sondern `TK_INT` emittieren, Punkt dem nächsten
   Token überlassen.

2. Lookahead-Regel in `scanNumber()`:
   ```
   if cur == '.' && isAlpha(peek(1)) → INT-Token stoppen, Punkt nicht konsumieren
   if cur == '.' && isDigit(peek(1)) → Float weiterlesen
   ```

3. Testfälle:
   ```lyx
   var s: pchar := 42.toStr();       // OK: Int-Call
   var f: f64   := 42.0;             // OK: Float-Literal
   var g: f64   := 42.0.toStr();     // OK: Float dann Methode (rarer Fall)
   ```

**Akzeptanzkriterien:**
- `42.toStr()` und `3.14` parsen beide korrekt
- Kein Regressions-Fehler in bestehenden Float-Tests

### WP-1.1-C: Compound-Token Longest-Match ✅

**Ziel:** Multi-Zeichen-Operatoren `??`, `?.`, `|>`, `|~`, `...`, `..`
werden zuverlässig vor ihren einzeichigen Präfixen erkannt.

**Aktueller Stand:** Einige Compound-Tokens existieren (`TK_NULL_COAL = ??`,
`TK_PIPE`), aber die Scan-Reihenfolge im Lexer ist nicht durchgehend
nach Longest-Match geordnet.

**Zu implementieren:**

1. Scan-Tabelle im Lexer alphabetisch nach Länge sortieren:
   - `.` → zuerst prüfen: `...` (3), dann `..` (2), dann `.` (1)
   - `|` → zuerst `|~`, `|>`, dann `|`
   - `?` → zuerst `??`, `?.`, dann `?`
   - `!` → zuerst `!=`, dann `!`

2. Neue Token-Konstanten wo fehlend:
   ```
   TK_DOTDOTDOT  := ...  (spread/variadic)
   TK_DOTDOT     := ..   (range inclusive)
   TK_PIPE_OP    := |>   (pipe-forward)
   TK_PIPE_CAST  := |~   (pipe-cast)
   TK_QMARK_DOT  := ?.   (optional chaining)
   ```

3. Unit-Test: Alle Compound-Tokens in einer Datei, Lexer-Output verifizieren.

**Akzeptanzkriterien:**
- `a?.b` erzeugt `TK_IDENT TK_QMARK_DOT TK_IDENT` — kein `TK_QMARK TK_DOT`
- `0..10` erzeugt `TK_INT TK_DOTDOT TK_INT`
- `f |> g` erzeugt `TK_IDENT TK_PIPE_OP TK_IDENT`

### WP-1.2: Pratt-Expression-Parser ✅

**Ziel:** Den bestehenden "precedence climbing"-Ausdruck-Parser
(`src/parser.lyx:725`) durch einen vollständigen Pratt-Parser ersetzen.

**Warum:** Pratt-Parser sind leichter erweiterbar, haben klar separierte
Binding-Power-Tabellen und eliminieren die aktuellen Ad-hoc-Precedence-Prüfungen.

**Zu implementieren:**

1. **Binding-Power-Tabelle** — 15 Stufen, absteigend:

   | Stufe | Operator(en)                    | Assoziativität |
   |-------|---------------------------------|----------------|
   | 15    | `()` `[]` `.` `?.`              | Links          |
   | 14    | Unär `!` `-` `~`                | Rechts         |
   | 13    | `*` `/` `%`                     | Links          |
   | 12    | `+` `-`                         | Links          |
   | 11    | `<<` `>>`                       | Links          |
   | 10    | `&`                             | Links          |
   | 9     | `^`                             | Links          |
   | 8     | `\|`                            | Links          |
   | 7     | `..` `...`                      | Links          |
   | 6     | `<` `<=` `>` `>=`               | Links          |
   | 5     | `==` `!=`                       | Links          |
   | 4     | `&&`                            | Links          |
   | 3     | `\|\|`                          | Links          |
   | 2     | `??`                            | Rechts         |
   | 1     | `\|>` `\|~`                     | Links          |

2. **Einstiegsfunktion** `parseExprPrec(minBP: int64): int64`:
   - `parsePrimary()` liefert das linke Atom
   - Loop: Schau auf nächstes Token, hole `infixBP(op)`, prüfe gegen `minBP`
   - Rekursiver Aufruf mit `infixBP(op) + 1` für Links-assoziativ

3. **ConstExpr-Einschränkung**: Separates Flag `inConstExpr: int64` auf dem
   Parser-Objekt; gesetzt bei `con`-Deklarationen, `@if`-Direktiven und
   Array-Größen-Ausdrücken. `parseExprPrec` prüft: Calls und Closures sind
   verboten → Compile-Fehler.

4. **Migration**: Alle bestehenden `parseExpr*`-Callsites auf neuen Pratt-Einstieg
   umleiten; alte Climbing-Funktionen entfernen.

**Akzeptanzkriterien:**
- `1 + 2 * 3` → `7` (korrekte Präzedenz)
- `a?.b?.c` → linkslastiger Baum
- `a ?? b ?? c` → rechtslastiger Baum
- `con N: int64 := foo();` → Compile-Fehler „function call in const expression"
- Alle bestehenden Parser-Tests unverändert grün

### WP-2.2-A: Match-Exhaustiveness ⬜

**Ziel:** Compile-Fehler wenn ein `match`-Ausdruck nicht alle möglichen
Enum-Varianten abdeckt und kein `_`-Wildcard vorhanden ist.

**Aktueller Stand:** Stub in `sema.lyx:1208`: `"Full exhaustiveness checking
requires enum variant analysis"` — gibt derzeit nur eine Warnung aus.

**Zu implementieren:**

1. In der Sema-Phase beim Verarbeiten von `NK_MATCH`:
   - Typ des Match-Ausdrucks bestimmen
   - Falls es ein Enum-Typ ist: alle deklarierten Varianten aus der Symtab laden
   - Für jede `NK_MATCH_CASE` die abgedeckten Varianten markieren
   - Falls nicht alle Varianten belegt UND kein Wildcard (`_`) → Fehler

2. Enum-Varianten-Set in der Symtab: Für jeden Enum-Typ speichern wir die
   Menge der Member-Namen. Beim Sema-Pass werden diese in einem bitmask-basierten
   Set (bis 64 Varianten) oder einer pchar-Liste (>64) verwaltet.

3. Fehlerformat:
   ```
   error: match does not cover variant 'Error' of enum Result
     at line 42, col 5
     hint: add case Error(...) => { ... } or a wildcard _ => { ... }
   ```

**Syntax:**
```lyx
enum Color { Red, Green, Blue }

match c {
  case Red   => { ... }
  case Green => { ... }
  // Fehler: Blue nicht abgedeckt
}
```

**Akzeptanzkriterien:**
- Obiges Beispiel → Compile-Fehler mit Variantenname
- `_ => { ... }` als letzte Case → kein Fehler
- Nicht-Enum-Match-Ausdrücke → keine Exhaustiveness-Prüfung (nur Warnung)

### WP-2.2-B: Defer-Scope-Semantik ⬜

**Ziel:** `defer`-Statements werden garantiert am Ende des umschließenden
Blocks ausgeführt (LIFO-Reihenfolge), auch bei frühem `return`.

**Aktueller Stand:** Lexer/Parser unterstützen `defer` (WP-AS-07). IR-Lowering
und Codegen fehlen noch — der deferred Stmt wird aktuell ignoriert.

**Zu implementieren:**

1. **IR-Lowering** (`src/ir_lower.lyx`):
   - Bei `NK_DEFER`: den Stmt-Baum in eine Deferred-Liste des aktuellen
     Block-Kontexts einreihen (LIFO-Stack pro Scope-Tiefe).
   - Bei `NK_RETURN` und Scope-Ende: alle aufgesammelten Deferred-Stmts in
     umgekehrter Reihenfolge als IR-Instruktionen vor dem `irRet` einfügen.

2. **Verschachtelte Scopes:**
   ```lyx
   {
     defer cleanup1();   // ausgeführt nach cleanup2
     {
       defer cleanup2(); // ausgeführt zuerst beim Verlassen des inneren Blocks
     }
     // cleanup2 läuft hier
   }
   // cleanup1 läuft hier
   ```
   Jede Block-Tiefe hält ihre eigene Defer-Liste.

3. **Panic-Sicherheit:** Falls später `panic()` implementiert wird, müssen
   Deferred-Stmts auch bei Panic laufen (Stack-Unwinding). Für v0.9.0:
   Defer nur bei normalem Kontrollfluss.

4. **Einschränkung:** `defer` innerhalb von `defer` ist ein Fehler.

**Syntax:**
```lyx
fn process(path: pchar): int64 {
  var fd: int64 := open(path, 0, 0);
  if (fd < 0) { return -1; }
  defer close(fd);     // läuft garantiert beim Verlassen

  if (readError()) { return -2; }  // close() wird trotzdem aufgerufen
  return 0;            // close() wird aufgerufen
}
```

**Akzeptanzkriterien:**
- `defer` vor frühzeitigem `return` → deferred Code läuft
- Mehrere `defer` in einem Block → LIFO-Reihenfolge
- `defer` in verschachtelten Blöcken → innerer Scope zuerst
- `defer defer x;` → Compile-Fehler

### WP-2.2-C: Switch-Fallthrough-Verbot ⬜

**Ziel:** Implizites Fallthrough zwischen `case`-Zweigen eines `switch` ist
ein Compile-Fehler. Jeder Case-Body muss explizit mit `break` oder `return`
enden.

**Aktueller Stand:** Sema prüft Fallthrough aktuell nicht.

**Zu implementieren:**

In `sema.lyx`, beim Traversieren von `NK_SWITCH`/`NK_CASE`:
- Kontrollfluss-Analyse: ist der letzte erreichbare Stmt eines Case-Bodies
  ein `NK_BREAK`, `NK_RETURN`, `NK_THROW`, oder `NK_CONTINUE`? → OK
- Andernfalls → Fehler: `"switch case may fall through; add 'break' or 'return'"`

Explizite Fallthrough-Direktive (optional für v0.9.0):
```lyx
switch (x) {
  case 1 => {
    doSomething();
    fallthrough;  // explizit erlaubt
  }
  case 2 => {
    doMore();
    break;
  }
}
```

**Akzeptanzkriterien:**
- Case ohne abschließendes `break`/`return` → Fehler
- Case mit `break` → kein Fehler
- `default` ohne `break` → Fehler
- Leerer Case-Body → Fehler (oder Warnung + implizites break)

### WP-3.1: Triple Modular Redundancy (TMR) ⬜

**Ziel:** Variablen mit `@redundant`-Annotation werden dreifach im Speicher
gehalten. Lesezugriffe führen automatisch Majority-Voting durch; bei erkanntem
Bit-Flip wird die korrupte Kopie selbst-geheilt.

**Anwendungsfall:** Sicherheitskritische Systeme (Avionik, Raumfahrt, Medizin),
wo Single-Event-Upsets (SEU) durch kosmische Strahlung Daten korrumpieren können.

**Zu implementieren:**

1. **Lexer/Parser:** `@redundant` als Annotation-Keyword für `var`-Deklarationen.
   ```lyx
   @redundant var sensorValue: int64 := 0;
   ```
   Parser setzt `VAR_FLAG_REDUNDANT`-Bit in `NK_VAR_DECL.iVal`.

2. **Sema:** Beim Verarbeiten von `NK_VAR_DECL` mit `VAR_FLAG_REDUNDANT`:
   - Drei Speicher-Slots reservieren statt einem: Offsets `base`, `base+8`, `base+16`
   - Den Sema-Typ-Eintrag mit `TY_REDUNDANT`-Flag markieren

3. **IR-Lowering / Codegen:**
   - **Schreiben:** Jede Zuweisung `sensorValue := x` → drei `irStore`-Instruktionen
     an die drei Slots
   - **Lesen:** Jeder Lesezugriff → `irCall __tmr_read(a, b, c)` — gibt den Majority-
     Wert zurück und repariert die abweichende Kopie

4. **`__tmr_read` Builtin** (als intrinsische Funktion in jedem Backend):
   ```
   __tmr_read(a, b, c):
     if a == b → return a (und schreibe a an c falls c != a)
     if a == c → return a (und schreibe a an b falls b != a)
     if b == c → return b (und schreibe b an a falls a != b)
     else      → return a  // triple mismatch, wähle erste Kopie
   ```
   Direkt als Inline-Assembler im Backend (3 CMP + 2 CMOV + 1 MOV für x86_64).

5. **Einschränkungen v0.9.0:**
   - Nur für skalare Integer-Typen (`int64`, `int32`, `int8`)
   - Keine Arrays oder Structs
   - Kein Thread-Safety

**Akzeptanzkriterien:**
- `@redundant var x: int64 := 5;` belegt 24 Bytes statt 8
- Alle drei Kopien werden bei Zuweisung aktualisiert
- Direktes Korrumpieren einer Kopie mit `poke64(addr+8, 0xDEAD)` → nächster
  Leseaufruf gibt richtigen Wert zurück und hat Kopie repariert
- Normale (nicht-redundante) Variablen: keine Performance-Regression

### WP-3.2: Secure Post-Patching (.meta_safe) ⬜

**Ziel:** Kompilierte Binaries enthalten eine `.meta_safe`-Section mit
CRC32-Hashes der Code-Sektionen. Ein Laufzeit-Prüfer kann damit Code-Integrität
verifizieren (Schutz gegen unbefugte Patches oder SEU-Korrumption im Flash).

**Zu implementieren:**

1. **Compiler-Pipeline-Extension** (`src/lyxc.lyx`):
   Neuer Pass nach dem Binary-Writer, aktiviert durch `--meta-safe`-Flag.

2. **4096-Byte-Seiten-Isolation:**
   Den `.text`-Abschnitt auf 4096-Byte-Grenzen ausrichten. Jede Seite wird
   separat gehasht → granulare Integrität pro Code-Page.

3. **CRC32-Berechnung:**
   ```
   for each 4096-byte page in .text:
     hash[i] = crc32(page_data, 4096)
   ```
   Eigene CRC32-Implementierung im Compiler (keine externe Bibliothek).

4. **`.meta_safe`-Section:**
   - Format: Magic (4 Bytes `0x4D455441`) + PageCount (4 Bytes) +
     Array von `{pageOffset: uint32, crc32: uint32}` Einträgen
   - In ELF: neue Section mit `SHT_NOTE`-Typ, `SHF_ALLOC | SHF_READONLY`
   - In PE: neue Section `.meta` mit `IMAGE_SCN_MEM_READ`

5. **Laufzeit-Verifier** (`std/meta_safe.lyx`):
   ```lyx
   pub fn MetaSafeVerify(): int64   // 0=OK, -1=corrupted
   pub fn MetaSafeGetPageHash(pageIdx: int64): int64
   ```

**Akzeptanzkriterien:**
- `lyxc --meta-safe hello.lyx` erzeugt Binary mit `.meta_safe`-Section
- `readelf -S out` zeigt `.meta_safe`
- `MetaSafeVerify()` gibt 0 zurück bei unverändertem Binary
- Nach `dd if=/dev/urandom of=out bs=1 count=1 seek=0x1000 conv=notrunc` →
  `MetaSafeVerify()` gibt -1 zurück

### WP-4.1-A: Struct-Feld-Packing `at(offset)` ⬜

**Ziel:** Exakte Kontrolle über Struct-Feld-Offsets für Memory-Mapped I/O,
Protokoll-Frames und hardware-nahe Programmierung.

```lyx
type UART_Regs = struct {
  DR:   uint32 at(0x00);   // Data Register
  SR:   uint32 at(0x04);   // Status Register
  BRR:  uint32 at(0x08);   // Baud Rate Register
  CR1:  uint32 at(0x0C);   // Control Register 1
  CR2:  uint32 at(0x10);   // Control Register 2
}
```

**Zu implementieren:**

1. **Parser:** `at(expr)` als optionalen Suffix nach dem Feldtyp.
   Neues Flag `FIELD_FLAG_PACKED_OFFSET` im `NK_FIELD_DECL.iVal`.
   `iVal.bits[32:63]` = angegebener Offset-Wert.

2. **Sema:**
   - Prüfen: Offset-Ausdrücke müssen ConstExpr sein
   - Prüfen: Felder dürfen sich nicht überlappen
   - Prüfen: Offsets aufsteigend geordnet (Warnung wenn nicht)
   - Gesamtgröße = max(Offset + Sizeof(FieldType)) über alle Felder

3. **Codegen:**
   - Bei Feldnamen-Lookup: statt berechneten Offset den expliziten Offset nutzen
   - `poke32(base + 0x08, val)` statt `poke32(base + autoOffset, val)`

4. **`packed` Struct-Annotation:** Auch `@packed` auf Struct-Ebene ohne
   explizite Offsets → kein Padding zwischen Feldern (binäre Ausrichtung 1).
   ```lyx
   @packed type Frame = struct { magic: uint16; len: uint8; data: uint8; }
   ```

**Akzeptanzkriterien:**
- `offsetof(UART_Regs, BRR)` = 8 (statt auto-berechnet)
- Overlapping offsets → Compile-Fehler
- `@packed` Struct → `sizeof(Frame)` = 4 (kein Padding)

### WP-4.1-B: `@big_endian` Byte-Swap-Emission ⬜

**Ziel:** Felder die mit `@big_endian` annotiert sind, erzeugen beim Lesen/
Schreiben automatisch Byte-Swap-Instruktionen (x86: `BSWAP`, ARM64: `REV`).

```lyx
type IPv4Header = struct {
  @big_endian total_len: uint16;   // Network byte order
  @big_endian src_ip:    uint32;
  @big_endian dst_ip:    uint32;
}

var hdr: IPv4Header;
hdr.total_len := 1500;             // emittiert: mov + bswap
var len: uint16 := hdr.total_len;  // emittiert: mov + bswap
```

**Zu implementieren:**

1. **Parser:** `@big_endian` als Feld-Annotation in Struct-Deklarationen.
   Setzt `FIELD_FLAG_BIG_ENDIAN` in `NK_FIELD_DECL.iVal`.

2. **Codegen (x86_64):**
   - Nach `irLoad` auf ein `FIELD_FLAG_BIG_ENDIAN`-Feld: `BSWAP rax` emittieren
   - Vor `irStore` auf ein solches Feld: `BSWAP rax` emittieren
   - `uint16`: `XCHG al, ah` (kein `BSWAP` für 16-Bit)
   - `uint32`: `BSWAP eax`
   - `uint64`: `BSWAP rax`

3. **Codegen (ARM64):**
   - `REV16`, `REV32`, `REV64` je nach Feldbreite

4. Einschränkung: nur auf Integer-Felder (`uint8` bis `uint64`).

**Akzeptanzkriterien:**
- `hdr.src_ip := 0xC0A80001;` → im Binary: `BSWAP` vor `MOV [addr]`
- Round-trip: `hdr.src_ip := x; var y := hdr.src_ip;` → `y == x`
- Falsche Annotation auf `f64`-Feld → Compile-Fehler

### WP-4.3: Windows PE32+ Finalisierung 🔄

**Ziel:** Der PE32+-Writer (`src/backend/pe/write_pe.lyx`) erzeugt vollständig
ausführbare `.exe`-Dateien für Windows x86_64. Import-Tabelle und Base-
Relocation-Blocks sind korrekt befüllt.

**Aktueller Stand:** `write_pe.lyx` (671 Zeilen) und `dynamic_linker.lyx`
(410 Zeilen) vorhanden. Noch offen: Base-Relocation-Blocks und vollständiger
IAT-Wiring-Test.

**Zu implementieren:**

1. **Base Relocation Block** (`.reloc`-Section):
   - Für jede Absolute-Adresse im `.text` (z.B. `lea rax, [rip+symbol]`-
     Adressen die vom Image-Base abhängen): Relocation-Eintrag schreiben
   - Format: `IMAGE_BASE_RELOCATION` Header + Array von 16-Bit-Einträgen
     (Typ `IMAGE_REL_BASED_DIR64 = 10` für 64-Bit-Pointer)
   - Sectioncharacteristic: `IMAGE_SCN_CNT_INITIALIZED_DATA | IMAGE_SCN_MEM_READ |
     IMAGE_SCN_MEM_DISCARDABLE`

2. **IAT (Import Address Table) vollständig wiren:**

   - IAT-Section auf beschreibbar setzen (Loader muss schreiben)

3. **ASLR-Kompatibilität:**
   - `IMAGE_DLLCHARACTERISTICS_DYNAMIC_BASE` ist gesetzt (bereits im Code)
   - Alle Code-Referenzen müssen relativ sein (RIP-relativ auf x86_64) →
     kein Bedarf an Absolut-Relokationen im normalen Textbereich

4. **Test:** `hello.lyx` → `hello.exe` → läuft auf Windows 10/11
   (Prüfung mit Wine auf Linux, oder echtem Windows)
