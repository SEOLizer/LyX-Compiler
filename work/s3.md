# Lyx Amazon S3-Client (`std/cloud/s3`) — Fahrplan

Dieses Dokument beschreibt den vollständigen Entwicklungsplan für `std/cloud/s3`,
den offiziellen S3-Client von Lyx. Ziel ist eine vollständige, reine
Lyx-Implementierung — ohne AWS SDK, ohne libcurl — auf Basis von
`std/net/https` + eigenem **AWS Signature Version 4 (SigV4)**-Layer.

**Kompatibilität:** Amazon S3, MinIO, Cloudflare R2, DigitalOcean Spaces,
Backblaze B2 und jeder andere S3-kompatible Objektspeicher.

**Konvention:** WP-S3-NN (S3 Client, Nummer). Status-Symbole: ✅ Erledigt,
🔄 In Arbeit, ⬜ Offen.

---

## Vision

```lyx
import std.io;
import std.cloud.s3;

pub fn main(): int64 {
  var s3: int64 := S3Connect("us-east-1", "AKIA…", "wJaFuCDe…");
  S3BucketCreate(s3, "mein-bucket");

  // Datei hochladen
  var data: pchar := "Hallo aus Lyx!";
  S3PutObject(s3, "mein-bucket", "hello.txt", data, StrLen(data), "text/plain");

  // Datei herunterladen
  var size: int64 := 0;
  var content: int64 := S3GetObject(s3, "mein-bucket", "hello.txt", &size);
  PrintStr(content as pchar);
  PrintStr("\n");

  // Objekte auflisten
  var list: int64 := S3ListObjects(s3, "mein-bucket", "", 100);
  var i: int64 := 0;
  while (i < S3ListCount(list)) {
    PrintStr(S3ListGetKey(list, i));
    PrintStr(" (");
    PrintInt(S3ListGetSize(list, i));
    PrintStr(" Bytes)\n");
    i := i + 1;
  }
  S3ListFree(list);

  // Presigned URL erzeugen (7 Tage gültig)
  var url: pchar := S3PresignGet(s3, "mein-bucket", "hello.txt", 604800);
  PrintStr(url);
  PrintStr("\n");

  S3DeleteObject(s3, "mein-bucket", "hello.txt");
  S3Close(s3);
  return 0;
}
```

## AWS SigV4 — Vollständige Signatur-Referenz

### Übersicht (4 Tasks)

```
Task 1: Canonical Request
Task 2: String to Sign
Task 3: Signing Key ableiten
Task 4: Authorization-Header aufbauen
```

### Task 1: Canonical Request

```
CanonicalRequest =
  Method + '\n'
  + CanonicalURI + '\n'
  + CanonicalQueryString + '\n'
  + CanonicalHeaders + '\n'
  + SignedHeaders + '\n'
  + HexSHA256(body)
```

- **CanonicalURI:** URI-Pfad, jedes Segment prozent-enkodiert (Buchstaben/Ziffern/`-._~` unverändert)
- **CanonicalQueryString:** Query-Parameter nach Key aufsteigend sortiert, Key + Value prozent-enkodiert, mit `=` verbunden, mit `&` getrennt
- **CanonicalHeaders:** Headernamen lowercase, nach Name sortiert, je Zeile `name:trimmed_value\n`
- **SignedHeaders:** Semicolon-getrennte lowercase Headernamen (dieselbe Reihenfolge wie CanonicalHeaders)
- **HexSHA256(body):** `"e3b0c44298fc1c149afbf4c8996fb924…"` für leeren Body; sonst SHA256 des Body-Bytes

Immer zu signierende S3-Header:
```
host
x-amz-content-sha256
x-amz-date
```

### Task 2: String to Sign

```
StringToSign =
  "AWS4-HMAC-SHA256" + '\n'
  + <ISO8601-Timestamp> + '\n'      // z. B. "20240115T120000Z"
  + <CredentialScope> + '\n'        // z. B. "20240115/eu-central-1/s3/aws4_request"
  + HexSHA256(CanonicalRequest)
```

### Task 3: Signing Key

```
kSecret  = "AWS4" + secret_access_key
kDate    = HMAC-SHA256(kSecret,   date_str)          // "20240115"
kRegion  = HMAC-SHA256(kDate,     region)            // "eu-central-1"
kService = HMAC-SHA256(kRegion,   "s3")
kSigning = HMAC-SHA256(kService,  "aws4_request")
```

### Task 4: Authorization-Header

```
Authorization: AWS4-HMAC-SHA256
  Credential=<access_key>/<date>/<region>/s3/aws4_request,
  SignedHeaders=host;x-amz-content-sha256;x-amz-date,
  Signature=HexEncode(HMAC-SHA256(kSigning, StringToSign))
```

### Pflicht-Header für jede S3-Anfrage

| Header | Wert | Beschreibung |
|--------|------|--------------|
| `Host` | `<bucket>.s3.<region>.amazonaws.com` | Virtual-hosted-style |
| `X-Amz-Date` | `20240115T120000Z` | ISO 8601, UTC |
| `X-Amz-Content-SHA256` | `HexSHA256(body)` | SHA256 des Body |
| `Authorization` | `AWS4-HMAC-SHA256 …` | Vollständige Signatur |
| `Content-Length` | `<n>` | Nur bei PUT/POST |
| `Content-Type` | `application/octet-stream` | Nur bei PUT |

### WP-S3-01: SHA-256 & HMAC-SHA256 ⬜

**Ziel:** SHA-256 und HMAC-SHA256 als neue Lyx-Units implementieren — sie sind
die kryptographische Grundlage für SigV4 und können später auch anderen Units
dienen (z. B. TLS-Handshake, Passwort-Hashing).

**SHA-256 Algorithmus:**

SHA-256 verarbeitet Eingaben in 512-Bit-Blöcken (64 Bytes) mit 64 Runden.

```
Interne Zustandsvariablen (8 × uint32, Big-Endian):
  H0..H7 = [6A09E667, BB67AE85, 3C6EF372, A54FF53A,
             510E527F, 9B05688C, 1F83D9AB, 5BE0CD19]

Konstanten K[0..63] = erste 32 Bits des Nachkommateils der Kubikwurzel
  der ersten 64 Primzahlen (standardisiert in FIPS 180-4)

Padding:
  Nachricht + 0x80 + 0x00* + [orig_bit_len: uint64 BE]
  → Gesamtlänge ≡ 0 mod 64

Pro 64-Byte-Block:
  W[0..15]  = Block-Wörter
  W[16..63] = W[i-16] + σ0(W[i-15]) + W[i-7] + σ1(W[i-2])
  64 Kompressions-Runden: a,b,c,d,e,f,g,h
  H0..H7 += a..h
```

- `sha256Init(state)` — initialisiert die 8 Zustandswörter
- `sha256Block(state, block)` — verarbeitet einen 64-Byte-Block
- `sha256Finalize(state, msg, totalLen) → void` — Padding + letzter Block
- `SHA256(data, len, out[32])` — Haupt-API: schreibt 32 Bytes in `out`
- `SHA256Hex(data, len) → pchar` — gibt 64-Zeichen-Hex-String zurück (heap-allokiert)

**HMAC-SHA256:**
```
HMAC(key, msg) =
  SHA256((key XOR opad) || SHA256((key XOR ipad) || msg))
  ipad = 0x36 × 64, opad = 0x5C × 64
  Wenn key > 64 Bytes: key = SHA256(key)
```
- `HMACSHA256(key, keyLen, data, dataLen, out[32])` — schreibt 32 Bytes
- `HMACSHA256Hex(key, keyLen, data, dataLen) → pchar` — 64-Zeichen-Hex

**Hex-Kodierung:**
- `HexEncode(data, len) → pchar` — gibt lowercase-Hex-String zurück
- `HexDecode(hex, outLen) → int64` — Hex-String → Bytes

**Dateien:**
- `std/crypto/sha256.lyu`

**Akzeptanzkriterien:**
- `SHA256Hex("", 0)` == `"e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"`
- `SHA256Hex("abc", 3)` == `"ba7816bf8f01cfea414140de5dae2ec73b00361bbef0469121afc7f88ac2e7a"`
- `SHA256Hex("a" × 55, 55)` == bekannter Referenzwert (Padding-Grenze)
- `HMACSHA256Hex("key", 3, "The quick brown fox jumps over the lazy dog", 43)` ==
  `"f7bc83f430538424b13298e6aa6fb143ef4d59a14946175997479dbc2d1a3cd8"`
- `HexEncode` + `HexDecode` sind invers zueinander

### WP-S3-02: AWS SigV4 Signing-Layer ⬜

**Ziel:** Den vollständigen AWS Signature Version 4-Prozess implementieren —
von der Canonical Request bis zum fertigen Authorization-Header.

**Zu implementieren:**

- `S3SigCtx`-Struct (für einen einzelnen Request):
  ```
  S3SigCtx {
    method=pchar; host=pchar; path=pchar; query=pchar
    date_time=pchar         // "20240115T120000Z"
    date_short=pchar        // "20240115"
    region=pchar; service=pchar     // "s3"
    access_key=pchar; secret_key=pchar
    body_sha256=pchar       // HexSHA256(body), 64 Zeichen
    headers=int64           // Array S3Header* (name + value)
    header_count=int64
    signed_headers=pchar    // "host;x-amz-content-sha256;x-amz-date"
  }
  ```
- `sigv4CanonicalURI(path, out)` — URI-Enkodierung (nur unreservierte Zeichen unverändert)
- `sigv4CanonicalQuery(query, out)` — Query-String sortieren + enkodieren
- `sigv4CanonicalHeaders(ctx, out)` — lowercase, sortiert, newline-getrennt
- `sigv4CanonicalRequest(ctx, out)` — alle 6 Zeilen zusammensetzen
- `sigv4CredentialScope(ctx, out)` — `"20240115/eu-central-1/s3/aws4_request"`
- `sigv4StringToSign(ctx, canonical_req, out)`
- `sigv4DeriveKey(secret_key, date, region, service, out[32])`
  — 4× HMAC-SHA256-Chain: kDate → kRegion → kService → kSigning
- `sigv4Signature(signing_key, string_to_sign) → pchar` — 64 Hex-Zeichen
- `sigv4AuthHeader(ctx) → pchar`
  — vollständiger `Authorization: AWS4-HMAC-SHA256 …`-Header
- `sigv4AddRequiredHeaders(ctx, body, bodyLen)`
  — fügt `X-Amz-Date`, `X-Amz-Content-SHA256`, `Host` zum ctx hinzu

**Prozent-Enkodierung für Canonical URI:**
```
Erlaubt ohne Enkodierung: A-Z a-z 0-9 - _ . ~
Alles andere: %XX (Hex, uppercase)
S3-Spezialfall: Schrägstrich im Key wird NICHT enkodiert (nur Bucket-/Key-Grenze)
```

**Timestamp-Format:**
```
X-Amz-Date: 20240115T120000Z   (ISO 8601, UTC, kein Trennzeichen)
→ Muss via sys_time(2) oder ähnlichem aus der System-Uhr gelesen werden
```
Interner Syscall: `sys_clock_gettime(CLOCK_REALTIME)` → UTC-Timestamp

**Dateien:**
- `std/cloud/s3.lyu` (Abschnitt: SigV4)

**Akzeptanzkriterien:**
- Bekannte AWS-SigV4-Testvektoren (öffentlich: [aws.amazon.com/general/sigv4](https://docs.aws.amazon.com/general/latest/gr/sigv4-create-canonical-request.html)) bestanden:
  - `GET /` für `s3.amazonaws.com` mit bekannten Credentials → exakt gleiche Signatur
- `sigv4CredentialScope` gibt korrekten String zurück
- `sigv4DeriveKey` gibt stabilen 32-Byte-Schlüssel zurück (deterministisch)
- Authorization-Header hat exakt das Format `AWS4-HMAC-SHA256 Credential=…,SignedHeaders=…,Signature=…`

### WP-S3-03: HTTPS-Transport-Erweiterung für S3 ⬜

**Ziel:** Einen vollständigen HTTP/HTTPS-Client für S3 implementieren, der
beliebige Methoden (PUT, DELETE, HEAD) und beliebige Header unterstützt.
`std/net/https` bietet nur `HTTPSGet` / `HTTPSPost` — für S3 reicht das nicht.

**Zu implementieren:**

- Interne Funktion `s3HttpSend(host, port, use_tls, method, path, headers, header_count, body, body_len) → S3Response*`
  — nutzt intern: `TLSInit` / `TLSConnect` / `TLSWrite` / `TLSRead` (aus https.lyu)
  für HTTPS; oder direktes `write`/`read` für HTTP (MinIO-Dev ohne TLS)
- HTTP/1.1-Request aufbauen (ASCII, keine Bibliothek):
  ```
  METHOD /path HTTP/1.1\r\n
  Host: bucket.s3.region.amazonaws.com\r\n
  Header1: Value1\r\n
  …\r\n
  \r\n
  [body bytes]
  ```
- HTTP/1.1-Response parsen:
  - Statuszeile: `HTTP/1.1 200 OK`
  - Header: bis zur Leerzeile
  - Body: `Content-Length`-Bytes lesen (oder bis Verbindung schließt)
  - Chunked Transfer Encoding: `Transfer-Encoding: chunked` unterstützen
    (S3 nutzt das für einige Antworten)
- `S3Response`-Struct (per `mmap`):
  ```
  S3Response {
    status_code=int64
    headers=int64; header_count=int64   // Array S3Header*
    body=int64; body_len=int64
  }
  ```
- `S3Header`-Struct: `{ name=pchar; value=pchar }`
- `S3ResponseFree(resp) → void`
- `S3ResponseGetHeader(resp, name) → pchar` — case-insensitive Suche
- Verbindungs-Keep-Alive: TLS-Verbindung pro `S3Conn` offen halten;
  bei `Connection: close` neu verbinden

**Dateien:**
- `std/cloud/s3.lyu` (Abschnitt: HTTP-Transport)

**Akzeptanzkriterien:**
- `s3HttpSend` für `GET https://s3.amazonaws.com/` gibt valide HTTP-Antwort zurück
- PUT mit 1 MB Body: vollständig übertragen (keine Truncation)
- Chunked-Encoding: Body korrekt reassembliert
- `S3ResponseGetHeader(resp, "etag")` findet Header case-insensitiv
- HTTP 4xx/5xx: Statuscode korrekt in `status_code` gespeichert (kein Absturz)

### WP-S3-04: S3Conn-Typ & Connect/Close ⬜

**Ziel:** Den öffentlichen `S3Conn`-Struct und alle Verbindungsvarianten
implementieren.

**Zu implementieren:**

- Struct `S3Conn` (per `mmap`):
  ```
  S3Conn {
    region=pchar; access_key=pchar; secret_key=pchar
    endpoint=pchar          // z. B. "s3.eu-central-1.amazonaws.com"
                            // oder "localhost:9000" für MinIO
    use_path_style=bool     // false = virtual-hosted; true = path-style
    use_tls=bool            // false nur für lokale MinIO-Dev-Instanzen
    port=int64              // 443 (HTTPS) oder 9000 (MinIO)
    last_status=int64       // HTTP-Statuscode der letzten Operation
    last_error_code=pchar   // aus XML <Code> (z. B. "NoSuchKey")
    last_error_msg=pchar    // aus XML <Message>
    tls_ctx=int64           // TLS-Kontext (für Keep-Alive, optional)
    sig_buf=int64           // Scratch-Buffer für SigV4-Berechnungen
  }
  ```
- `S3Connect(region, access_key, secret_key) → int64`
  — Standard AWS S3; endpoint = `s3.<region>.amazonaws.com`
- `S3ConnectEndpoint(region, access_key, secret_key, endpoint, use_tls, path_style) → int64`
  — für MinIO, R2, etc.; `endpoint` kann `"localhost:9000"` sein
- `S3ConnectR2(account_id, access_key, secret_key) → int64`
  — Cloudflare R2: endpoint = `<account_id>.r2.cloudflarestorage.com`
- `S3ConnectMinio(host, port, access_key, secret_key) → int64`
  — MinIO local: path-style, ohne TLS
- `S3Close(conn) → void`
- `S3LastStatus(conn) → int64` — letzter HTTP-Statuscode
- `S3LastError(conn) → pchar` — letzter XML-Fehlertext
- `S3LastErrorCode(conn) → pchar` — z. B. `"NoSuchBucket"`

**Endpoint-Auflösung intern:**
```
Virtual-hosted: <bucket>.s3.<region>.amazonaws.com/<key>
Path-style:     s3.<region>.amazonaws.com/<bucket>/<key>
Custom:         <endpoint>/<bucket>/<key>
```

**Dateien:**
- `std/cloud/s3.lyu`

**Akzeptanzkriterien:**
- `S3Connect` + `S3Close` ohne Fehler
- `S3ConnectMinio("localhost", 9000, …)` → korrekte path-style Anfragen
- `S3LastErrorCode` nach 404-Antwort: `"NoSuchKey"`
- `S3ConnectEndpoint` mit benutzerdefiniertem Endpoint: korrekte URL-Bildung

### WP-S3-05: Bucket-Verwaltung & XML-Parser ⬜

**Ziel:** Bucket-Operationen implementieren und einen minimalen XML-Parser
für S3-Antworten bauen.

**Bucket-Operationen:**

- `S3BucketCreate(conn, bucket) → bool`
  — `PUT /<bucket>` (ggf. mit LocationConstraint-Body für Nicht-us-east-1)
- `S3BucketDelete(conn, bucket) → bool`
  — `DELETE /<bucket>` (nur wenn leer)
- `S3BucketExists(conn, bucket) → bool`
  — `HEAD /<bucket>` → 200 oder 404
- `S3ListBuckets(conn) → int64`
  — `GET /` → S3BucketList*; parst `<ListAllMyBucketsResult><Buckets>` XML
- Internes XML: `S3BucketList { buckets=int64; count=int64 }`
  - `S3BucketListCount(list) → int64`
  - `S3BucketListGetName(list, i) → pchar`
  - `S3BucketListFree(list) → void`

**Minimaler XML-Parser (`s3XmlParser`, intern):**

S3 verwendet einfaches, flaches XML ohne Namespaces. Kein vollständiger
DOM nötig — nur extrahieren:
- `s3XmlGetTag(xml, tag) → pchar` — erster Wert von `<tag>…</tag>`
- `s3XmlGetAllTags(xml, tag, outCount) → pchar*` — alle Werte eines Tags (für Listen)
- `s3XmlGetNested(xml, outer, inner) → pchar` — `<outer><inner>…</inner></outer>`

Relevante XML-Strukturen:
```xml
<!-- Fehler -->
<Error><Code>…</Code><Message>…</Message></Error>

<!-- Bucket-Liste -->
<ListAllMyBucketsResult>
  <Buckets><Bucket><Name>…</Name></Bucket></Buckets>
</ListAllMyBucketsResult>

<!-- ListObjectsV2 -->
<ListBucketResult>
  <Contents><Key>…</Key><Size>…</Size><ETag>…</ETag></Contents>
  <IsTruncated>…</IsTruncated>
  <NextContinuationToken>…</NextContinuationToken>
</ListBucketResult>

<!-- Multipart-Init -->
<InitiateMultipartUploadResult>
  <UploadId>…</UploadId>
</InitiateMultipartUploadResult>
```

**Dateien:**
- `std/cloud/s3.lyu`

**Akzeptanzkriterien:**
- `S3BucketCreate` + `S3BucketExists` → true
- `S3BucketDelete` + `S3BucketExists` → false
- `S3ListBuckets` gibt alle vorhandenen Buckets zurück
- `s3XmlGetTag("<Error><Code>NoSuchKey</Code></Error>", "Code")` == `"NoSuchKey"`
- `S3BucketCreate` für existierenden Bucket ohne Fehler (BucketAlreadyOwnedByYou ignorieren)

### WP-S3-06: Objekt-CRUD ⬜

**Ziel:** Die Kern-Dateioperationen: Hochladen, Herunterladen, Löschen,
Metadaten lesen, Kopieren.

**Zu implementieren:**

- `S3PutObject(conn, bucket, key, data, len, content_type) → bool`
  — `PUT /<bucket>/<key>`; setzt Content-Type + Content-Length + SigV4
- `S3PutObjectFile(conn, bucket, key, local_path, content_type) → bool`
  — liest Datei via sys_read und ruft S3PutObject auf
- `S3GetObject(conn, bucket, key, outLen) → int64`
  — `GET /<bucket>/<key>`; gibt heap-allokierten Buffer zurück (mmap)
- `S3GetObjectFile(conn, bucket, key, local_path) → bool`
  — downloaded und schreibt direkt in Datei (kein komplettes In-Memory-Buffer)
- `S3GetObjectRange(conn, bucket, key, offset, length, outLen) → int64`
  — `GET` mit `Range: bytes=<offset>-<offset+length-1>`
- `S3DeleteObject(conn, bucket, key) → bool`
  — `DELETE /<bucket>/<key>`
- `S3DeleteObjects(conn, bucket, keys, count) → int64`
  — `POST /<bucket>?delete` mit XML-Body (Multi-Object-Delete); gibt Anzahl gelöschter zurück
- `S3HeadObject(conn, bucket, key) → int64`
  — `HEAD /<bucket>/<key>`; gibt S3ObjectMeta-Ptr zurück (oder 0 wenn 404)
- `S3ObjectExists(conn, bucket, key) → bool`
  — HeadObject → 200 oder 404
- `S3CopyObject(conn, src_bucket, src_key, dst_bucket, dst_key) → bool`
  — `PUT /<dst_bucket>/<dst_key>` mit `x-amz-copy-source: /<src_bucket>/<src_key>`
- `S3ObjectMeta`-Struct:
  ```
  S3ObjectMeta {
    key=pchar; etag=pchar
    size=int64; last_modified=pchar
    content_type=pchar; version_id=pchar
  }
  ```
- `S3ObjectMetaFree(meta) → void`
- `S3GetETag(conn, bucket, key) → pchar` — nur ETag via HeadObject

**Dateien:**
- `std/cloud/s3.lyu`

**Akzeptanzkriterien:**
- `S3PutObject` + `S3GetObject`: identischer Byte-Vergleich (1 Byte bis 10 MB)
- `S3DeleteObject` + `S3ObjectExists` → false
- `S3HeadObject` gibt korrekte Größe zurück
- `S3CopyObject`: Quell-Objekt unverändert, Ziel-Objekt identisch
- `S3GetObjectRange`: gibt exakt `length` Bytes ab `offset` zurück
- `S3DeleteObjects` mit 3 Keys: alle 3 gelöscht

### WP-S3-07: ListObjects & Paginierung ⬜

**Ziel:** Objekte in einem Bucket auflisten — inklusive Paginierung für Buckets
mit mehr als 1.000 Objekten.

**Zu implementieren:**

- `S3ListObjects(conn, bucket, prefix, max_keys) → int64`
  — `GET /<bucket>?list-type=2&prefix=<prefix>&max-keys=<n>`
  → gibt S3ObjectList-Ptr zurück
- `S3ListObjectsNext(conn, bucket, prefix, max_keys, list) → int64`
  — Folge-Seite via `continuation-token=<S3ListGetToken(list)>`
  → gibt neue S3ObjectList zurück (oder 0 wenn `IsTruncated == false`)
- `S3ListAll(conn, bucket, prefix) → int64`
  — iteriert automatisch alle Seiten, gibt vollständige Liste zurück
  (nur für moderate Objektzahlen; für sehr große Buckets Seiten manuell iterieren)
- `S3ListWithDelimiter(conn, bucket, prefix, delimiter) → int64`
  — simuliert Ordnerstruktur: `delimiter="/"` → CommonPrefixes = "Unterordner"
- `S3ObjectList`-Struct:
  ```
  S3ObjectList {
    objects=int64; count=int64; alloc=int64
    is_truncated=bool
    continuation_token=pchar
    common_prefixes=int64; prefix_count=int64   // "Unterordner"
  }
  ```
  Elemente: Array `S3ObjectMeta*`
- `S3ListCount(list) → int64`
- `S3ListGetKey(list, i) → pchar`
- `S3ListGetSize(list, i) → int64`
- `S3ListGetETag(list, i) → pchar`
- `S3ListGetModified(list, i) → pchar`
- `S3ListIsTruncated(list) → bool`
- `S3ListGetToken(list) → pchar` — Continuation Token für nächste Seite
- `S3ListGetPrefix(list, i) → pchar` — i-ter CommonPrefix (Unterordner)
- `S3ListPrefixCount(list) → int64`
- `S3ListFree(list) → void`

**Dateien:**
- `std/cloud/s3.lyu`

**Akzeptanzkriterien:**
- 5 Objekte hochladen, `S3ListObjects` → `S3ListCount == 5`
- `S3ListObjects` mit `prefix="img/"` filtert korrekt
- 1.500 Objekte: `S3ListAll` liefert alle 1.500 (automatische Paginierung)
- `S3ListWithDelimiter` mit `delimiter="/"`: CommonPrefixes enthält Unterordner-Namen

### WP-S3-08: Multipart-Upload ⬜

**Ziel:** Große Dateien (> 5 GB, oder bereits ab 5 MB für optimalen Durchsatz)
in parallelen Parts hochladen.

**Hintergrund:** S3-Limit: Einzelner PUT-Request max. 5 GB. Empfohlen ab 100 MB.
Jeder Part muss mindestens 5 MB groß sein (außer dem letzten).

**Zu implementieren:**

- `S3MultipartBegin(conn, bucket, key, content_type) → pchar`
  — `POST /<bucket>/<key>?uploads`
  → parst `<UploadId>` aus XML; gibt Upload-ID zurück (oder 0)
- `S3MultipartUploadPart(conn, bucket, key, upload_id, part_num, data, len) → pchar`
  — `PUT /<bucket>/<key>?partNumber=<n>&uploadId=<id>`
  → gibt ETag aus Response-Header zurück (für Complete-Body nötig)
  `part_num`: 1-basiert, maximal 10.000 Parts
- `S3MultipartComplete(conn, bucket, key, upload_id, etags, count) → bool`
  — `POST /<bucket>/<key>?uploadId=<id>`
  → Body: XML mit allen Parts + ETags:
  ```xml
  <CompleteMultipartUpload>
    <Part><PartNumber>1</PartNumber><ETag>"etag1"</ETag></Part>
    <Part><PartNumber>2</PartNumber><ETag>"etag2"</ETag></Part>
  </CompleteMultipartUpload>
  ```
- `S3MultipartAbort(conn, bucket, key, upload_id) → bool`
  — `DELETE /<bucket>/<key>?uploadId=<id>` (S3 gibt Speicher für Parts frei)
- Convenience-Funktion `S3PutObjectMultipart(conn, bucket, key, data, len, content_type, part_size) → bool`
  — zerlegt Daten in Parts der Größe `part_size` (min. 5 MB),
  führt Begin + UploadPart×N + Complete durch;
  bei Fehler: Abort

**Optimale Part-Größe:**
```
< 100 MB:   einzelner PUT (kein Multipart nötig)
100 MB – 1 GB: part_size = 16 MB
1 GB – 10 GB:  part_size = 64 MB
> 10 GB:        part_size = 256 MB
```

**Dateien:**
- `std/cloud/s3.lyu`

**Akzeptanzkriterien:**
- 50 MB Datei in 5 × 10-MB-Parts hochladen → korrekt zusammengesetzt (Byte-Vergleich)
- `S3MultipartAbort` nach Begin + 1 Part: kein Objekt in Bucket, Upload-ID ungültig
- `S3PutObjectMultipart` für 200-MB-Datei: korrekt hochgeladen
- ETags aller Parts in Complete-Body korrekt (mit + ohne umgebende `"`)

### WP-S3-09: Presigned URLs ⬜

**Ziel:** Zeitlich begrenzte URLs erzeugen, die temporären Zugriff auf
S3-Objekte erlauben — ohne AWS-Credentials im Browser oder beim Endnutzer.

**Hintergrund:** Presigned URLs enthalten die SigV4-Signatur als Query-Parameter
statt als Header (`Authorization`-Header). Damit kann jeder (z. B. ein Browser)
die URL direkt aufrufen.

**Zu implementieren:**

- `S3PresignGet(conn, bucket, key, expires_sec) → pchar`
  — erzeugt presigned GET-URL (gültig für `expires_sec` Sekunden)
- `S3PresignPut(conn, bucket, key, expires_sec, content_type) → pchar`
  — presigned PUT-URL (Upload ohne Credentials)
- `S3PresignDelete(conn, bucket, key, expires_sec) → pchar`
  — presigned DELETE-URL
- `S3PresignHead(conn, bucket, key, expires_sec) → pchar`

**SigV4 Query-String-Signatur (statt Authorization-Header):**
```
X-Amz-Algorithm=AWS4-HMAC-SHA256
X-Amz-Credential=<access_key>%2F<date>%2F<region>%2Fs3%2Faws4_request
X-Amz-Date=<timestamp>
X-Amz-Expires=<seconds>
X-Amz-SignedHeaders=host
X-Amz-Signature=<signature>
```

Unterschied zur Header-Signatur:
- `X-Amz-Content-SHA256` nicht signiert (Body unbekannt bei GET)
- `HexSHA256(body)` → fixer Wert `"UNSIGNED-PAYLOAD"` für den Canonical Request
- Alle Query-Parameter werden in `CanonicalQueryString` aufgenommen und sortiert

**Dateien:**
- `std/cloud/s3.lyu`

**Akzeptanzkriterien:**
- `S3PresignGet` erzeugt URL der Form `https://bucket.s3.region.amazonaws.com/key?X-Amz-Algorithm=…`
- URL ist im Browser direkt abrufbar (curl-Test) und liefert korrekte Datei
- URL nach `expires_sec` Sekunden ungültig (403 von S3)
- `S3PresignPut` + curl `--upload-file file.txt <url>` lädt Datei hoch
- Presigned URL mit falschen Credentials → 403 (kein Crash, kein Leak)

## Offene Fragen

- **SHA-256 als eigene Unit oder inline?** `std/crypto/sha256.lyu` wäre
  wiederverwendbar (TLS-Handshake, JWT, allgemeines Hashing) — empfohlen.
  Alternativ: inline in s3.lyu für minimale Abhängigkeiten.
- **Server-Side Encryption (SSE):** S3 unterstützt SSE-S3 (`x-amz-server-side-encryption: AES256`),
  SSE-KMS und SSE-C (Kunden-Key). Für einfachen Client: SSE-S3 via Header ist
  trivial — separates WP oder direkt in S3-06?
- **Object Tagging:** `PUT /<bucket>/<key>?tagging` — nützlich für Lifecycle-Rules.
  Separates WP oder Teil von S3-06?
- **Transfer Acceleration:** `<bucket>.s3-accelerate.amazonaws.com` — nur anderer
  Endpoint, kein Code-Änderung nötig.
- **Parallelität:** Multipart-Parts könnten parallel hochgeladen werden
  (mehrere gleichzeitige TLS-Verbindungen). Für initiale Implementierung:
  sequenziell ausreichend?
- **Streaming-GET:** Für sehr große Objekte wäre ein Callback-basiertes API
  (`S3GetObjectStream(conn, bucket, key, callback, ctx)`) sinnvoll — außerhalb
  des initialen Scope?
