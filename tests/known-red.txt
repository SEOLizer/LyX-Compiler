# tests/known-red.txt — Tests, die laufen, aber bekannt rot sind.
#
# Stand mit lyxc 1.1.2C neu gemessen (#1153). Ein Eintrag ist entfallen:
# as/test_defer_early_return endet mit exit=42, und 42 ist im Bestand die
# Erfolgskonvention — der Runner wertet sie inzwischen als gruen. Die fuenf
# ALSA-Eintraege, die einzeln gruen sind, bleiben stehen: sie haengen an einem
# Geraet und sind im Lauf nach den anderen ALSA-Tests wieder rot
# (Geraetekonkurrenz). Genau dafuer traegt die Liste `!flaky`.
#
# Warum es diese Liste gibt: ein roter Test, der aus einem Ziel entfernt wird,
# damit das Ziel gruen wird, ist danach unsichtbar — genau der Verfall, den
# #1004 und #1112 aufgedeckt haben. Eintraege hier laufen weiter mit, brechen
# das Ziel aber nicht ab.
#
# Regeln:
#   * Jeder Eintrag traegt ein Issue. Ohne Issue verschwindet der Defekt.
#   * Wird ein Eintrag wieder gruen, meldet der Runner das und das Ziel wird
#     ROT. Die Liste kann also nicht stillschweigend veralten.
#   * Pfad relativ zur Repo-Wurzel, ein Eintrag je Zeile, `#` beginnt einen
#     Kommentar.
#
# Gelesen von: tests/run_lyx_tests.sh (tests/lyx/**), Ziel `test-known-red`
# im Makefile (die .sh-Eintraege).

# ── #1153: Erstlauf von tests/run_lyx_tests.sh an einem Make-Ziel.
#    Brauchen Soundkarte bzw. MySQL-Server. Die ALSA-Laufzeitfaelle tragen
#    `!flaky`: ohne Soundkarte scheitern sie, mit einer laufen sie mal durch und
#    mal nicht (Geraetekonkurrenz, wenn 19 Tests nacheinander das Geraet oeffnen).
#    Ohne die Markierung faerbt jeder zufaellige Durchlauf das Ziel rot, weil ein
#    bekannt roter Test gruen wurde. Die Kategorie "uebersetzen ja, ausfuehren
#    nein" fehlt noch — das ist #1153.

#    Echte Defekte oder verrotteter Testcode:

# #1705: hier standen vier Rote, die beim Scharfschalten der CI (#1696)
# aufgefallen waren. Drei sind behoben und deshalb gestrichen:
#   * test_debug_fn.lyx / test_retval.lyx trugen drei Felder, die `Series`
#     nicht mehr hat (nullBitmap, capacity, memFlags) — Tests nachgezogen.
#   * test_debug_data.lyx laeuft durch; das [exit=1] war nicht geraete-
#     abhaengig, sondern inzwischen weg.
# Der vierte, test_mysql_full_query.lyx, galt als "Timeout nach 60s" und
# damit als dienstabhaengig. Er war es nicht: `MySQLFetchRow` nahm `res` als
# Wert und erhoehte darin `current_row`, sodass `while (row > 0)` endlos lief.
# Mit `ref` laeuft der Test durch — er bleibt hier nur, weil er einen
# laufenden MySQL-Dienst braucht und in der CI keinen findet.
# #1696: zeitabhaengig. Der Test wartet auf inotify-Ereignisse und lief beim
# Nachmessen in 2 von 8 Durchlaeufen in den Timeout — auch ohne Fremdlast, mit
# Last haeufiger. In einer CI, die auf geteilten Maschinen laeuft, waere das
# ein Dauerflackern; `!flaky` haelt ihn im Lauf, ohne das Ziel rot zu machen.
tests/lyx/test_wp10_inotify.lyx !flaky               # [timeout] zeitabhaengig (#1705)

# ── #2418: TLS-Interop gegen OpenSSL. Faellt NUR UNTER LAST, darum `!flaky`.
#
#    Belegt: der Lyx-Server gibt `empfangen 18 GET / HTTP/1.0` aus und kommt
#    nicht bis zu seinem "fertig" (Exitcode 141 = SIGPIPE); s_client laeuft
#    exakt bis in sein `timeout` (gemessen 40,04 s bei timeout 40), seine
#    Ausgabe bricht beim `---` vor den Nutzdaten ab. BEIDE Seiten warten;
#    SIGPIPE ist die Folge, nicht die Ursache.
#
#    Reproduzierbar mit `nproc` Dauerlast-Prozessen: ohne Last 3 von 3
#    Laeufen gruen, mit Last 6-8 PASS / 3-5 FAIL. Im CI (EPYC in VM,
#    parallele Jobs) ebenso — develop war deshalb ab 2026-11-08 07:24 rot.
#
#    Drei Theorien sind gemessen und widerlegt: Vollpufferung von s_clients
#    stdout, SHA-NI (#2391), und das Zeitfenster (`sleep 30`/`timeout 40`
#    statt 3/25 aenderte nichts). Naechster Schritt: strace auf beide Seiten.
#
#    Der Eintrag verschwindet, sobald die Ursache behoben ist. Solange laeuft
#    der Test weiter mit — er ist nicht aus dem Lauf genommen, nur aus
#    `make test`, damit ein Flake nicht jeden PR blockiert.
tests/tls13_interop_openssl_test.sh !flaky
